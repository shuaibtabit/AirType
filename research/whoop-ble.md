# WHOOP 5.0 BLE source audit

Inspected on November 11, 2026. Both repositories were cloned into the task's separate `work/` directory. AirType contains its own CoreBluetooth implementation and has no package dependency on either project.

## WhoopBLE

- **Revision and license.** Tag `0.1.22`, commit `b60f874f1c37a97fcf30ca6c928e465a4becf627`. MIT, copyright Asher Cohen. The mirror's Swift package declares Swift 5.9, macOS 13+ and iOS 16+. The package compiled on Apple Silicon under macOS 26.3 and Swift 6.2.4. [Package manifest](https://github.com/Asherlc/whoop-ble-swift/blob/b60f874f1c37a97fcf30ca6c928e465a4becf627/Package.swift) · [License](https://github.com/Asherlc/whoop-ble-swift/blob/b60f874f1c37a97fcf30ca6c928e465a4becf627/LICENSE)
- **Public surface.** `WhoopBleClient.discover() async` returns an optional `WhoopDevice`, `connect(to:)` is async throwing, and `imuSamples()` returns `AsyncStream<WhoopImuSample>`. Register the stream before calling `startImuStreaming() async throws`. Cleanup is `stopStreaming() async` followed by `disconnect()`. Samples expose strap seconds, fractional ticks, position and count within a frame, acceleration in g, and angular velocity in rad/s. `realtimeSamples()` is a separate stream for heartbeat, orientation and optical data. [Client](https://github.com/Asherlc/whoop-ble-swift/blob/b60f874f1c37a97fcf30ca6c928e465a4becf627/ios/WhoopBleClient.swift) · [Sample type](https://github.com/Asherlc/whoop-ble-swift/blob/b60f874f1c37a97fcf30ca6c928e465a4becf627/ios/WhoopBleSample.swift)
- **Limit for this experiment.** The parser handles R21 and dedicated IMU types 51/52. For R21 it emits one row per accelerometer sample and zero-fills gyro when that column has fewer samples. The public start path writes realtime HR, optical, and realtime-record commands, then 106 to enable IMU. It does not send the WHOOP 5.0/MG raw producer start command 81 documented by NOOP. The retained capture includes valid R21 data from a bonded upstream session. The package documentation describes using an existing OS bond and records command refusal from an unbonded macOS probe. A working parse and macOS build leave device activation on a standalone Mac unresolved. [Parser](https://github.com/Asherlc/whoop-ble-swift/blob/b60f874f1c37a97fcf30ca6c928e465a4becf627/ios/WhoopBleFrameParser.swift) · [Protocol and bond notes](https://github.com/Asherlc/whoop-ble-swift/blob/b60f874f1c37a97fcf30ca6c928e465a4becf627/Documentation/WHOOP-BLE-Protocol.md)

## NOOP

- **Revision and license.** Commit `2a1de7609843b095505274ad6fc811757210be80`. NOOP's original code and docs use PolyForm Noncommercial 1.0.0. The repository distinguishes its protocol facts from its original code and documents separate terms for bundled dependencies. AirType uses the published protocol facts and has no NOOP source dependency. [License](https://github.com/ryanbr/noop/blob/2a1de7609843b095505274ad6fc811757210be80/LICENSE)
- **macOS support.** The SwiftUI app targets macOS 13+ and its README lists Apple Silicon and Intel builds. The upstream release is not notarized. AirType did not install or launch NOOP. The 5.0/MG deep-data support remains experimental. The standard heart-rate profile can stream independently of the proprietary encrypted command channel. [NOOP macOS and strap support](https://github.com/ryanbr/noop#platform-status) · [Xcode project definition](https://github.com/ryanbr/noop/blob/2a1de7609843b095505274ad6fc811757210be80/project.yml)
- **Actual six-axis path.** `BLEManager.startGroundTruthRawCapture(sessionId:)` starts a manually stopped session. `captureRawAccel(seconds:)` provides a bounded path despite the name referring only to acceleration. The bonded 5.0/MG path sends opcode 81 with `[01]` followed by opcode 106 with `[01,01]`. Stop sends opcode 82 with `[01]` followed by 106 with `[01,00]`. NOOP reports hardware verification for this sequence and reports that 106 alone can acknowledge without starting the producer. `Whoop5RawImu.decode(_:)` reads six signed columns in a 1,244-byte buffer. Its source cites 1,423 buffers from a real 5.0 on firmware 50.40.1.0, with plausible gravity and gyro motion. This is upstream evidence. [Capture design and verification](https://github.com/ryanbr/noop/blob/2a1de7609843b095505274ad6fc811757210be80/docs/RAW_DATA_CAPTURE.md) · [BLE implementation](https://github.com/ryanbr/noop/blob/2a1de7609843b095505274ad6fc811757210be80/Strand/BLE/BLEManager.swift#L2196) · [Decoder](https://github.com/ryanbr/noop/blob/2a1de7609843b095505274ad6fc811757210be80/Packages/WhoopProtocol/Sources/WhoopProtocol/Whoop5RawImu.swift)

## AirType implementation and risks

AirType uses the NOOP-documented `fd4b` service with command `0002`, response notifications on `0003`, and data notifications on `0005`. Some upstream notes also name a separate `1150` service. This proof of concept targets `fd4b` only. It sends a confirmed Hello before subscribing to the protected channels, following the current macOS app's callback order. This differs from the ordering in the NOOP protocol overview. The confirmed write can invoke OS bonding. AirType's capture command requires explicit opt-in, has bounded timeouts, and does one attempt per run. [5.0/MG service and Hello](https://github.com/ryanbr/noop/blob/2a1de7609843b095505274ad6fc811757210be80/docs/PROTOCOL_WHOOP5.md#connection-and-frame-format) · [macOS Hello and subscription order](https://github.com/ryanbr/noop/blob/2a1de7609843b095505274ad6fc811757210be80/Strand/BLE/BLEManager.swift#L6733)

AirType checks Format 1 header CRC16 and body CRC32, uses request sequence to report firmware response status when available, and counts only live type 43/R21 records. ATT acknowledgment and firmware acceptance are separate events. The Bluetooth write callbacks pace the commands. A valid live buffer is the first evidence of data delivery. Historical type 47 frames and dedicated types 51/52 are outside this capture path. The CSV emits paired samples up to the smaller count in a partial frame, preserves both original counts, and supplies no estimated per-sample device time for that frame. Host receive time indicates delivery and buffering. Keep the raw counts because firmware or sensor configuration can change scaling and timing. [Format 1 transport](https://github.com/ryanbr/noop/blob/2a1de7609843b095505274ad6fc811757210be80/docs/PROTOCOL_TRANSPORT.md#format-1-framing) · [R21 layout and timestamps](https://github.com/ryanbr/noop/blob/2a1de7609843b095505274ad6fc811757210be80/docs/PROTOCOL_SENSORS.md#r21-six-axis-imu)

NOOP reports a single active encrypted bond and describes refused encryption when the phone app holds it. A new Mac bond can require re-pairing the phone. Keep the user's setup in place during initial discovery. If testing requires a bond change, agree on the interruption and recovery steps with the user first. NOOP's newer protocol notes document R21 against firmware 50.42.1.0, and WHOOP rolls out firmware updates in phases. Record the strap's actual firmware before testing. [NOOP pairing notes](https://github.com/ryanbr/noop#strap-support) · [WHOOP firmware notes](https://support.whoop.com/s/article/WHOOP-5-0-MG-Firmware-Release-Notes) · [WHOOP in-app pairing](https://support.whoop.com/s/article/Setting-Up-Your-WHOOP-4-0?language=en_US)

## Verification in this workspace

- AirType and WhoopBLE both compiled on Apple Silicon, macOS 26.3, Swift 6.2.4.
- Three AirType tests passed. They cover published command bytes, fragmented and corrupted frames, signed axes, partial counts, timestamp reconstruction and historical-frame exclusion.
- Offline replay of WhoopBLE's retained `imu-activation-capture.tsv` through AirType's parser decoded 45 live R21 frames and 4,499 paired samples with zero framing rejects. This fixture replay exercises the parser without Bluetooth.
- Verified the executable embeds the Bluetooth usage description and rejects a capture command without the opt-in. Discovery, bonding, live reception, firmware scaling and cleanup on the user's physical strap remain to be verified.
